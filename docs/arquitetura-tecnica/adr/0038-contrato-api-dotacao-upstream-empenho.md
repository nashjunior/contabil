# ADR-0038 · Contrato de API da Dotação — consulta por ente/exercício com saldo inline e ingestão em lote (upstream do empenho)

- **Status:** Proposta
- **Data:** 2026-07-26
- **Contexto:** [RAZ-140](../fluxo-execucao-operador-contrato-api.md) (Figma: Dotação/crédito orçamentário) pediu a tela de **visão/gestão de dotação por ente/exercício** — saldo disponível/bloqueado/empenhado, carga da LOA/crédito adicional em lote com resumo fail-soft, vínculo dotação→empenho — como upstream explícito do fluxo já contratado em [fluxo-execucao-operador-contrato-api.md](../fluxo-execucao-operador-contrato-api.md) ("não dá pra empenhar sem dotação"). O domínio já existe: `Dotacao`/`CreditoAdicional`/`SaldoDotacao` ([execucao-orcamentaria-despesa.md](../execucao-orcamentaria-despesa.md)) e o caso de uso `IngerirDotacoes` (fail-soft, [ADR-0013](./0013-persistencia-lote-fail-soft.md)) foram entregues em RAZ-65/66/80/81/82/89 — isso torna **obsoleto** o bullet do [§7 do doc de fluxo](../fluxo-execucao-operador-contrato-api.md#7-abertos-e-riscos) que dizia "`Dotacao` como agregado não existe em código ainda" (verdadeiro quando RAZ-79 foi escrito, falso hoje). O que **não** existe é a borda HTTP: nenhum `DotacaoController`, nenhuma entrada em `frontend/openapi/contrato-provisorio.yaml`. A reconciliação RAZ-129 (Aurélio) já abriu duas issues de backend adjacentes — **RAZ-135** (`GET /dotacoes/{id}/saldo`, *in_progress*) e **RAZ-136** (`GET /dotacoes?classificacao=&cursor=` + cadastros de apoio, *backlog*, "provável escopo F2") — mas nenhuma cobre (a) a **listagem por ente/exercício com saldo inline** que a tela de gestão precisa para renderizar uma tabela sem N chamadas de saldo, nem (b) a **escrita** (`IngerirDotacoes` não tem HTTP nenhum).
- **Decisão:**
  1. **`GET /entes/{enteId}/execucao/dotacoes?exercicio=&busca=&cursor=&limit=`** — lista paginada (§6.1 do contrato) com o saldo **embutido na mesma linha** (`valorAutorizado`, `valorComprometido`, `saldoDisponivel` — espelha `SaldoDotacao` campo a campo, igual ao formato já definido em [§6.2 do fluxo](../fluxo-execucao-operador-contrato-api.md#62-consulta-de-saldo-alimenta-as-três-telas)), não uma referência que exige um segundo `GET .../saldo` por linha. `busca` filtra por prefixo/`ilike` de `classificacaoOrcamentaria` — é o mesmo parâmetro que a combo "Dotação" da tela de empenho (RAZ-102, `fluxo-execucao-operador-contrato-api.md §5.1`) precisa para o "combo — busca por classificação" que hoje não tem endpoint algum atrás dele.
  2. **Isso estreita o escopo de RAZ-136.** RAZ-136 tratou `GET /dotacoes?classificacao=&cursor=` como F2 ("cadastros de apoio... provável escopo F2"), agrupado com Credor/Contrato/Unidade Gestora (que não têm tabela própria e são F2 de fato). Dotação é diferente: já é agregado real com repositório real (`DotacaoRepository`) — falta só o método de listagem (`listarPorEnte`, não existe hoje, só `buscarPorId`) e um índice (`ix_dotacao_ente_exercicio`, não existe na V3 migration — só `unique(ente_id, id)`). Não há razão de domínio para empurrar isso para F2 quando RAZ-140 já contratualiza a tela que o consome **agora**; RAZ-136 deveria manter F2 só para Credor/Contrato/Unidade Gestora/classificação orçamentária estruturada. **Pede ratificação do Aurélio** — é uma correção de escopo de uma decisão já registrada (RAZ-129/RAZ-136), não uma decisão nova isolada.
  3. **`POST /entes/{enteId}/execucao/dotacoes:lote`** — espelha `IngerirDotacoes.executar(sessao, enteId, fixacoes, creditos)` 1:1: `{ "fixacoes": [...], "creditos": [...] }` → `207` fail-soft `{ "dotacoesInseridas": [...], "dotacoesAtualizadas": [...], "erros": [...] }`. RBAC dupla (`CRIAR` só se `fixacoes` não vazio, `ALTERAR` só se `creditos` não vazio) já é do use case, a borda HTTP não reimplementa. **Sem lote menor que isso** (não existe "fixar 1 dotação avulsa" como endpoint separado) — o próprio use case já trata lote-de-1 como caso normal do mesmo caminho, evita duplicar código para "singular" vs "lote" como o resto do domínio faz (empenho/liquidação, [ADR-0022](./0022-lote-pagamento-contrato-api-execucao.md)) só que aqui a decisão é a **oposta**: dotação **é** lote por natureza (carga de LOA é ingestão de estruturante, não ato individual — mesma leitura que already fecha o [ADR-0022 §8](./0022-lote-pagamento-contrato-api-execucao.md) para "empenho não tem lote porque não há precedente de negócio"; aqui o precedente é o inverso, a LOA inteira chega de uma vez).
  4. **`erros[].motivo` vira `erros[].codigo` + `mensagem`.** Hoje `DotacaoRepository.ErroItemLote` só tem `referencia`+`motivo` (texto livre — "dotação já existe (id duplicado)", "dotação não encontrada para o ente"). O envelope de erro do resto do contrato ([§6.1](../fluxo-execucao-operador-contrato-api.md#61-convenções-gerais)) usa `codigo` machine-readable (`ErroContrato.codigo()`). Antes de expor `POST /dotacoes:lote`, o backend precisa dar `codigo`s a esses dois motivos (ex.: `dotacao_duplicada`, `dotacao_nao_encontrada`) — pequeno, mas é pré-requisito, não detalhe da borda HTTP.
  5. **Sem "saldo bloqueado".** O issue pediu 3 saldos (disponível/bloqueado/empenhado). O domínio só tem 2: `valorAutorizado` e `valorComprometido` (= empenhado) → `saldoDisponivel` derivado. O estágio `(Reserva)` — pré-empenho reservando crédito antes do empenho, `saldoDisponivel → saldoReservado` — está **desenhado como opcional** em [execucao-orcamentaria-despesa.md](../execucao-orcamentaria-despesa.md#o-que-preciso-modelar-agregados-e-invariantes) mas **nunca foi implementado**: `SaldoDotacao` não tem `valorReservado`, `Dotacao` não tem `reservar()`/`liberar()`. A tela mostra a coluna "Bloqueado" (o issue pediu) mas com `— (n/d)`, nunca um valor inventado — se o produto quiser reserva/pré-empenho de verdade, é modelagem nova (agregado ganha estado, invariante nova de saldo), issue própria, não um campo de resposta a mais neste contrato.
  6. **Sem endpoint de trilha por dotação.** O padrão `GET .../trilha` existe só para liquidação ([ADR-0029](./0029-contrato-leitura-fila-aprovacao-trilha.md)). `IngerirDotacoes` já registra `execucao_dotacao_ingerida` em `AuditoriaEscrita`, mas é **um evento por lote inteiro** (resume quantas dotações/créditos, não decompõe por dotação individual) — suficiente para auditoria agregada, insuficiente para "mostrar a trilha desta dotação" na tela de detalhe. Fica como consulta futura, fora deste ADR.
- **Consequências:** duas issues novas de backend (`[BE] POST /dotacoes:lote` — expõe `IngerirDotacoes`; `[BE] GET /dotacoes` — listagem paginada com saldo inline + índice `ix_dotacao_ente_exercicio`), complementares a RAZ-135 (saldo por id, já em andamento) — nenhuma duplica a outra. RAZ-136 é revisitada para excluir a listagem de dotação do seu escopo F2 (mantém Credor/Contrato/UG/classificação estruturada). O componente Figma "Tabela — Dotações" (RAZ-140) já modela a coluna "Bloqueado" como gap visível — se a Reserva for implementada depois, é a mesma tabela, só a célula passa a ter dado real.
- **Alternativas consideradas:**
  - **Adiar a tela inteira para depois que RAZ-135/136 fecharem** — rejeitada: o próprio RAZ-140 é explícito que a UI nasce contra contrato proposto quando falta API (mesmo padrão do "Aviso de Gap" já usado em todas as telas RAZ-102/110/112); esperar bloquearia indefinidamente o desenho de um fluxo que já é upstream-crítico ("não dá pra empenhar sem dotação").
  - **Calcular saldo no cliente somando `GET /empenhos?dotacaoId=`** — rejeitada: reintroduz exatamente o problema que motivou `SaldosExecucaoPort`/lock de linha (saldo operacional é trava de concorrência no servidor, não relatório derivável no cliente); a lista de gestão deve ler o mesmo dado que a trava usa, não recalculá-lo.
  - **`PUT /dotacoes/{id}` para editar `valorAutorizado` direto** — rejeitada: contraria a disciplina de append/soma dos créditos adicionais (Lei 4.320 arts. 40–46, [Regra 4](../../05-regras-de-negocio.md)) — o valor só muda por lançamento de crédito rastreável (tipo + histórico + auditoria), nunca por sobrescrita.
