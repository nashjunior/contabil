# ADR-0016 · ControleAcesso na application: RBAC + MFA obrigatório para ações que movimentam recurso

- **Status:** Aceita
- **Data:** 2026-07-19
- **Contexto:** O piso F0 (`docs/13-nfr-e-operacao.md` §Piso de segurança F0; `docs/transversais/04-lgpd.md` §RBAC/MFA) exige MFA para perfis que movimentam recurso e autorização deny-by-default a partir de claim gov.br/ICP-Brasil verificada — nunca de header/query/body cru (`guardiao-seguranca` regra 2). O contrato `ServicoIdentidade` (ADR-0014, RAZ-8) já define `autenticar`/`autorizar`/`completarMfa`, mas nenhum use case o consumia (RAZ-33): `RegistrarFatoContabil`/`EstornarFatoContabil` recebiam só `TenantId`, sem checar permissão nem MFA. O adapter real gov.br/ICP-Brasil (validação de claim na borda HTTP) é escopo à parte (RAZ-5) — este ADR cobre o **lado de consumo**: como um use case protegido pede permissão.
- **Decisão:**
  1. `ControleAcesso` (`plataforma-domain.iam`) é um serviço de domínio (POJO, sem framework) que compõe `ServicoIdentidade`. Use cases protegidos declaram `Sessao usuarioAutenticado` como primeiro parâmetro de `executar(..)` — ao lado do `TenantId` que a RLS já exige (ArchUnit `executar_da_application_declara_tenant_id`) — e chamam `controleAcesso.exigir(usuarioAutenticado, enteId, recurso, acao)` como a primeira linha do método, antes de qualquer validação de negócio ou I/O.
  2. `exigir(..)` faz, em ordem: (a) confere que `enteId` da requisição bate com `usuarioAutenticado.ente()` — nunca confia num tenant que discorda da sessão verificada (anti-BOLA); (b) chama `ServicoIdentidade#autorizar` (deny-by-default); (c) para toda `Acao` diferente de `LER` ("movimenta recurso"), exige `usuarioAutenticado.mfaConcluido()` — senão `MfaRequeridoException`.
  3. RAZ-5/RAZ-58 entrega o adapter `plataforma-infra.iam.ServicoIdentidadeGovBrIcp`: com `siafic.iam.enabled=true`, valida JWT gov.br assinado (`RS256`) contra issuer/audience/chave pública configurados, aceita certificado ICP-Brasil apenas por fingerprint SHA-256 provisionado pelo ente, abre sessão nominal CPF/ente e aplica a matriz RBAC por objeto. Sem configuração explícita, `ServicoIdentidadeIndisponivel` segue como bean fail-closed (nunca autentica, nunca autoriza).
  4. `ServicoMascaramento.BaseLegalLgpd` não inclui `CONSENTIMENTO` — setor público usa só obrigação legal/política pública/interesse público (`04-lgpd` §Base legal; `guardiao-seguranca` regra 7).
  5. Não há autenticação por senha local no MVP: `ServicoIdentidade.Credencial` é `sealed` com `permits` fechado em `CredencialGovBr`/`CredencialCertificadoIcp` — travado em tempo de compilação, provado em `SemAutenticacaoPorSenhaLocalTest`. Se um dia houver login por senha, a política é Argon2id/bcrypt/scrypt com salt (`13-nfr` §piso F0), nunca hash simples.
- **Consequências:** Use case explicita RBAC/MFA no próprio fluxo de negócio (testável com mocks de `ServicoIdentidade`, sem precisar de contexto Spring) em vez de escondido num advisor AOP genérico — decisão deliberada: diferente do tenant/transação (RAZ-21/RAZ-23), a ação (`Acao.CRIAR`/`ESTORNAR`/…) correta para cada use case é conhecimento de negócio que um pointcut por assinatura não expressa sem metadado extra. Quando o IAM não está provisionado, todo use case protegido fica inacessível via o pipeline Spring de produção (correto — sem claim verificada não há autorização). Testes de integração que exercitam o pipeline podem substituir `ServicoIdentidade` por duplo permissivo, análogo a qualquer outro adapter substituído em teste.
- **Alternativas consideradas:** Autorização só via advisor AOP no mesmo padrão de `TenantContextUseCasesConfiguration` (rejeitada: exigiria anotação/metadado adicional por método para mapear `Acao`, perdendo a leitura direta "este use case pede isto" e divergindo do texto do critério de aceite); deixar `ServicoIdentidade` sem nenhum bean até RAZ-5 (rejeitada: contexto Spring falha tarde, no primeiro autowire, em vez de fail-closed explícito e testável desde já).
