# ADR-0022 · Lote é só no pagamento: contrato de API da execução da despesa não expõe lote em empenho/liquidação

- **Status:** Aceita
- **Data:** 2026-07-26
- **Ratificação:** RAZ-88 — Aurélio (arquitetura), 2026-07-26. Decisão de lote confirmada **sem ajuste**: lote só no pagamento (precedente da OB agrupadora); empenho e liquidação permanecem unitários. O gate de aprovação, deixado em aberto por este ADR, foi decidido em separado no [ADR-0023](./0023-gate-aprovacao-pagamento-segregacao.md) (é um segundo gate transacional, não só papel RBAC).
- **Contexto:** [RAZ-65](../execucao-orcamentaria-despesa.md) desenhou o domínio de execução (empenho/liquidação/pagamento) e deixou aberto, no [ADR-0013](./0013-persistencia-lote-fail-soft.md), se a UI teria operação em lote ("requisito de Produto a confirmar; a arquitetura já está coberta"). RAZ-66 (empenho) e RAZ-67 (liquidação/pagamento) já implementam os três use cases (`RegistrarEmpenho`/`RegistrarLiquidacao`/`RegistrarPagamento`) como operações **unitárias e atômicas** — cada uma trava saldo sob lock, monta lançamentos e chama `RegistrarFatoContabil` numa única transação ([ADR-0021](./0021-contabilizacao-execucao-despesa.md)). Faltava decidir, do lado de produto/contrato de API (RAZ-79), se algum desses três estágios expõe um endpoint de lote ao operador — decisão que muda a forma do contrato HTTP e, por consequência, o que o backend precisa suportar além do que RAZ-66/67 já entregaram.
- **Decisão:**
  - **Empenho:** **sem lote.** `POST /entes/{enteId}/execucao/empenhos` só aceita uma unidade. É um ato de gestão individual (credor + classificação + dotação + documento assinado); a única ingestão em massa do domínio — carga da LOA/dotações — é um bounded context de migração/ingestão, não uma tela de "empenhar em lote", e já está coberta pelo ADR-0013 nesse outro contexto.
  - **Liquidação:** **sem lote.** `POST /entes/{enteId}/execucao/liquidacoes` só aceita uma unidade. Cada liquidação carrega documento(s) de suporte próprios (art. 63 §2º); um lote esconderia a ligação 1:1 entre linha de erro e comprovante justamente no estágio que é o fato gerador da despesa (Lei 4.320 art. 35). Volume esperado (dezenas/dia num ente pequeno) não paga o custo de UX de misturar N liquidações num único envio.
  - **Pagamento:** **com lote.** Além de `POST /entes/{enteId}/execucao/pagamentos` (unitário), existe `POST /entes/{enteId}/execucao/pagamentos:lote`, que recebe uma lista (`toInsert` — sem `toUpdate`/`toDelete`, pagamento não se corrige por update) e devolve `processados[]` + `errors[]` (`HTTP 207`), meio a meio com o contrato do [ADR-0013](./0013-persistencia-lote-fail-soft.md). Justificativa: é o único estágio com precedente já modelado no domínio — a Ordem Bancária **agrupadora** (N pagamentos : 1 OB) existe porque a tesouraria processa remessa/borderô diária; o volume é real (fechamento) e o fail-soft evita que um beneficiário com dado bancário inválido trave os demais pagamentos aprovados do dia.
  - **O lote de pagamento não muda a unidade de atomicidade.** O endpoint de lote chama o mesmo caso de uso (`RegistrarPagamento`) uma vez por item, cada chamada sua própria transação — exatamente a definição do ADR-0013 ("unidade de atomicidade = o fato/registro individual; o lote é fail-soft **entre** unidades"). Não há transação guarda-chuva no lote; isso preserva o ADR-0021 (movimento + fato continuam all-or-nothing **por pagamento**) e não é uma exceção a ele.
  - **Contrato de erro único.** O `codigo` retornado em `errors[]` do lote é o mesmo `ErroContrato.codigo()` do use case individual (`saldo_insuficiente`, `beneficiario_obrigatorio`, `valor_invalido`, …) — a borda HTTP não inventa uma segunda taxonomia de erro para o caminho em lote.
  - **Aprovação (gate anterior ao pagamento) fica fora deste ADR.** O contrato propõe `Acao.APROVAR` sobre `execucao:pagamento` como estágio distinto de `Acao.CRIAR` (documento [fluxo-execucao-operador-contrato-api §6.6](../fluxo-execucao-operador-contrato-api.md#66-aprovação-o-gate-que-falta-em-código--contrato-proposto)), mas isso é lacuna de implementação hoje (`RegistrarPagamento` só checa `CRIAR`). **Ratificação RAZ-88:** o gate deixou de ser "aberto" — foi decidido no [ADR-0023](./0023-gate-aprovacao-pagamento-segregacao.md): é um **segundo gate transacional** (`APROVAR` + pré-condição de estado `aprovada` no pagamento), não só atribuição de papel via RBAC. A ação de aprovação continua **sem lote** nesta fase (§6.6).
- **Consequências:** Backend (RAZ-66/RAZ-67 e o que vier depois) só precisa de infraestrutura de lote fail-soft (particionamento de entrada, agregação de erro, resposta composta) no caminho de **pagamento**; empenho e liquidação continuam simples request/response 1:1, sem o custo adicional de orquestração em lote que não teria consumidor real na UI. A UI de pagamento em lote (§5.4 do doc de fluxo) é a única tela do fluxo de execução que precisa renderizar sucesso parcial a partir de `errors[]` — as outras duas telas tratam erro como falha simples do formulário. Custo: se a demanda real do ente divergir (ex.: prefeituras que de fato importam lote de empenhos de um sistema legado), este ADR precisa ser revisto — não é uma predição de tráfego, é uma leitura do processo de negócio descrito no domínio (RAZ-65) e no precedente da OB agrupadora.
- **Alternativas consideradas:**
  - **Lote uniforme nos três estágios** (empenho, liquidação e pagamento todos com endpoint `:lote`) — rejeitada: não há precedente de negócio para lote em empenho/liquidação (nenhum documento de domínio ou fluxo menciona "empenhar em lote"/"liquidar em lote"), e a liquidação especificamente perderia a rastreabilidade 1:1 documento↔valor num payload de lote. Simetria de API por si só não é motivo suficiente para expor uma operação sem consumidor real.
  - **Nenhum lote em lugar nenhum** (tudo unitário, inclusive pagamento) — rejeitada: ignoraria o padrão já existente na tesouraria (borderô/remessa diária) e forçaria o tesoureiro a N cliques sequenciais para uma rotina que já é, na prática, um lote — sem ganho de segurança (a atomicidade por item já é garantida pelo caso de uso individual, lote ou não).
  - **Transação única cobrindo o lote inteiro de pagamento** (tudo ou nada no lote) — rejeitada: contraria diretamente o ADR-0013 e reintroduz o problema que ele resolve (um item ruim bloqueando N válidos); também não é exigido por lei — cada pagamento é seu próprio fato contábil independente, não há Σ=Σ *entre* pagamentos diferentes.
