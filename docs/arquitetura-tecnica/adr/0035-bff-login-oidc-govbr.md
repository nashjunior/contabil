# ADR-0035 · BFF de login OIDC gov.br (autenticação geral, não assinatura)

- **Status:** Aceita
- **Data:** 2026-07-26 (Proposta) · 2026-07-26 (Aceita — ratificação de segurança RAZ-127)
- **Contexto:** As APIs de execução e consulta autenticam por requisição, sem estado, lendo `Authorization: Bearer <asserção gov.br>` no [`SessaoAutenticadaHttpResolver`](../../../bootstrap/src/main/java/br/contabil/consulta/SessaoAutenticadaHttpResolver.java), que chama `ServicoIdentidade.autenticar(new CredencialGovBr(assercao))` a cada chamada (RAZ-101/RAZ-105); a asserção é um JWT gov.br verificado por `VerificadorJwtGovBr` dentro de [`ServicoIdentidadeGovBrIcp`](../../../plataforma/plataforma-infra/src/main/java/br/contabil/plataforma/infra/iam/ServicoIdentidadeGovBrIcp.java). Já existe um BFF OAuth2 ([ADR-0017](./0017-bff-oauth-assinatura-govbr.md), RAZ-39/RAZ-31), mas o fluxo dele é escopado a `sign`/`signature_session` e produz apenas um token de **assinatura** guardado server-side — não produz uma asserção de **login geral** que o SPA possa apresentar como `Bearer`. O frontend (RAZ-120, [`AuthContext`](../../../frontend/src/shared/auth/AuthContext.tsx), README gap 4) hoje **sintetiza um bearer opaco de desenvolvimento**, sem curso em produção. Não há, no repositório, nenhum fluxo OIDC/OAuth2 de login que **obtenha** uma asserção gov.br real. A decisão pendente: qual mecanismo de login, e onde ele mora, sem quebrar a semântica stateless da API nem a fronteira domínio/borda ([ADR-0002](./0002-monolito-modular.md)/[ADR-0012](./0012-stack-jvm.md)).
- **Decisão:** Login é um **BFF server-side no `bootstrap`** que conduz o fluxo OIDC `authorization_code`+PKCE contra o gov.br com escopo de **autenticação** (`openid profile` — nunca `sign`), guarda a asserção gov.br **no servidor** e entrega ao navegador apenas um cookie de sessão `HttpOnly`+`Secure`+`SameSite=Lax`. Concretamente, espelhando a mecânica já validada no ADR-0017:
  1. Novo controller no `bootstrap` em rota própria (`/sessao/oauth/*`, separada de `/assinatura/oauth`). `GET /sessao/oauth/iniciar` cria `state`+`code_verifier` na `HttpSession` e redireciona ao `authorize` do gov.br; `GET /sessao/oauth/callback` valida o `state`, troca `code`→token (o `id_token`/`access_token` que o `VerificadorJwtGovBr` aceita), chama `ServicoIdentidade.autenticar` para **verificar** que a asserção abre uma `Sessao` válida (falha fechado se inválida, expirada ou sem concessão RBAC), guarda a asserção crua server-side atrelada à sessão e só então estabelece o cookie de sessão do navegador.
  2. O SPA **nunca recebe a asserção**. Chama a API com o cookie. O `SessaoAutenticadaHttpResolver` ganha um *fallback* **aditivo** por cookie de sessão: quando o cabeçalho `Authorization` está ausente mas há cookie de sessão BFF válido (mesmo composition root, monólito — ADR-0012), ele lê a asserção guardada e a **reverifica via `ServicoIdentidade.autenticar` a cada requisição** — a invariante de verificação stateless é preservada; nada de autoritativo é cacheado. O caminho por cabeçalho segue inalterado para chamadores externos/serviço (RAZ-84).
  3. CSRF: `state` server-side protege a perna OAuth; `SameSite=Lax` + token anti-CSRF protegem as chamadas de API mutantes autenticadas por cookie. MFA continua governado pelo caminho existente (`mfaConcluido` deriva de `identidade.mfaForteConcluido()`; movimentação exige MFA por [ADR-0016](./0016-controle-acesso-mfa-movimentacao-recurso.md)) — o BFF não reimplementa MFA, apenas conduz o login ao nível gov.br que faz `mfaConcluido` valer quando a ação exigir.
- **Consequências:** Domínio e application não mudam; o BFF de login é borda HTTP no `bootstrap`, coerente com ADR-0017/0012/0002. A asserção gov.br (PII/CPF) **nunca chega ao navegador** (LGPD/segurança). A API mantém semântica de verificação stateless mesmo no caminho por cookie (asserção reverificada a cada requisição); chamadores por cabeçalho não são afetados. O único estado server-side novo é o transiente OIDC (`state`/`code_verifier`) mais a asserção guardada ligada à sessão do navegador — a mesma classe de estado que o ADR-0017 já introduziu para assinatura. Credenciais (`client_id`/`client_secret` do escopo de login) vêm do cofre/ambiente ([ADR-0024](./0024-cofre-segredos-f0-env-passthrough.md)); sem elas o endpoint de login falha fechado no início do fluxo, preservando o startup local — como no ADR-0017. **Bloqueador externo:** o e2e real exige um cliente OIDC gov.br registrado para o escopo de login (`openid`) — acesso administrativo humano à conta gov.br do ente, mesma natureza do RAZ-39/RAZ-31; a mecânica redirect/callback/token/IAM/cookie é testável com stub local (como no ADR-0017). Runbook de provisionamento: [`RAZ-126-runbook-oidc-login-govbr`](../../operacao/RAZ-126-runbook-oidc-login-govbr.md). A revisão de segurança/LGPD/ICP-Brasil (co-dono segurança/Solange, **RAZ-127**) **ratificou este ADR para Aceita** em 2026-07-26, sob os três refinamentos vinculantes abaixo (que a impl [BE], RAZ-128, deve honrar). **Tratamento de erro do `callback` (RAZ-237, 2026-08-01):** por paridade com a **decisão 3 do [ADR-0039](./0039-contrato-leitura-assinatura-empenho-preview-retorno-oauth.md)** já aplicada ao BFF de assinatura, toda falha do callback (`state_ausente`/`state_invalido`/`oauth_recusado`/`code_ausente`/`login_oauth_provedor_indisponivel`) deixou de devolver corpo JSON cru — que o navegador do gov.br não tem onde renderizar — e passou a redirecionar `302` para a rota de login do SPA (`siafic.login.govbr.oauth.frontend-erro-uri`, default `/entrar`) com `?erro=<codigo ErroContrato §6.1>`; só a taxonomia estável trafega na query string, nunca texto livre do gov.br (R4/RAZ-152). O sucesso segue inalterado via `post-login-redirect-uri`. Sem toque em domínio/application (mesma classe de mudança da RAZ-158 para assinatura).
- **Refinamentos vinculantes (ratificação de segurança RAZ-127):**
  1. **Base legal do tratamento (LGPD).** O dado pessoal na asserção gov.br (CPF, nome) tratado no login tem base legal em **Lei 13.709/2018 (LGPD) art. 7º, II** (cumprimento de obrigação legal — escrituração/prestação de contas do SIAFIC) **e III** (execução de política pública), combinada com a **Lei 14.063/2020** (identidade digital gov.br) — **nunca consentimento** (art. 7º, I), vedado no setor público ([`04-lgpd`](../../transversais/04-lgpd.md) §Base legal; [ADR-0016](./0016-controle-acesso-mfa-movimentacao-recurso.md) §4). A operação de login declara finalidade+base legal na trilha (`04-lgpd` §"base legal amarrada à operação"). Reafirma a invariante já decidida: a asserção (PII) vive **server-side**, jamais em armazenamento alcançável por JS.
  2. **Ciclo de vida da sessão (anti-fixation + expiração + CSRF).** No `callback` bem-sucedido, **antes** de guardar a asserção e emitir o cookie, o BFF **regenera o id da `HttpSession`** (anti session-fixation); o *logout* invalida a sessão server-side (descarta a asserção). A vida útil efetiva do cookie é **limitada pela validade da asserção gov.br**: como a asserção é reverificada a cada requisição via `ServicoIdentidade` (Decisão §2), expiração/revogação/MFA são sempre autoritativas do gov.br, nunca cacheadas. O **token anti-CSRF é obrigatório** em toda chamada mutante autenticada por cookie — sua ausência **falha fechado** —, com `SameSite=Lax` como defesa em profundidade.
  3. **Nível de garantia e escopo mínimo.** O cliente OIDC de login deve ser registrado no nível de garantia gov.br **Prata/Ouro** para que `identidade.mfaForteConcluido()` (→ `mfaConcluido`) valha nas ações que movimentam recurso ([ADR-0016](./0016-controle-acesso-mfa-movimentacao-recurso.md) §2c; [`13-nfr`](../../13-nfr-e-operacao.md) §piso F0); login simples (`LER`) não exige MFA. Escopo mínimo **`openid profile`** (`profile` apenas para nome de exibição) — **nunca** `sign`/`signature_session` (esses são do [ADR-0017](./0017-bff-oauth-assinatura-govbr.md); cliente e escopo distintos, conforme o runbook). Fail-closed do `ente` por concessão RBAC (deny-by-default) e recusa de tenant divergente da sessão (anti-BOLA, ADR-0016 §2a) já estão cobertos pela Decisão e pelo runbook.
- **Alternativas consideradas:** (1) **SPA faz `authorization_code`+PKCE direto e guarda o token gov.br no navegador** — rejeitado: coloca uma asserção gov.br real em armazenamento alcançável por JS (exfiltração via XSS, exposição de PII/LGPD), contraria a invariante "token nunca sai do server-side" do ADR-0017, e é o próprio "menos recomendado" do RAZ-126. (2) **Processo de gateway/reverse-proxy separado injetando o cabeçalho** — rejeitado para F0/F1: adiciona um salto out-of-process a um monólito modular (ADR-0002/0012) sem necessidade; o *fallback* aditivo no resolvedor é o seam nativo do monólito. (3) **Cunhar um token de sessão opaco próprio e mapeá-lo à asserção server-side** — rejeitado: reverificar a asserção gov.br a cada requisição (pelo port existente) mantém fonte única de verdade para identidade/expiração/MFA e evita um ciclo de vida paralelo de token de sessão.
