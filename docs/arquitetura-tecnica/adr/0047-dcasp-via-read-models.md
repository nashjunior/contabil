# ADR-0047 · Demonstrações DCASP geradas a partir de read models do razão (reusa `GerarBalancete`/`BalancetePort`)

- **Status:** Aceita
- **Data:** 2026-08-01
- **Contexto:** O fechamento contábil (RAZ-206) precisa produzir as 4 demonstrações DCASP obrigatórias pela Lei 4.320/1964 arts. 101–106 (Balanço Orçamentário, Balanço Financeiro, Balanço Patrimonial, DVP — mapeamento confirmado em [docs/15-fechamento-contabil.md](../../15-fechamento-contabil.md) §Fontes/a revalidar). Hoje só existe o balancete (`GerarBalancete`/`Balancete`/`BalancetePort`, RAZ-97), que já segue [ADR-0007](./0007-read-models-cqrs.md) — leituras pesadas/relatórios são servidas por read models derivados, não pelo primary OLTP do razão, para não contender com a escrituração.
- **Decisão:**
  - **As 4 demonstrações DCASP são read models derivados, no mesmo padrão do balancete** — não uma nova fonte da verdade, nem uma tabela materializada mutável por fora do razão. Cada demonstração é uma consulta (view/query) sobre os fatos e lançamentos já registrados, filtrada por ente + exercício (+ mês, quando aplicável), reconstruível a qualquer momento a partir do razão.
  - **Reusa a infraestrutura existente, não duplica o motor de leitura.** Novo(s) port(s) em `razao-domain` (ex. `DemonstracaoContabilPort`, ou um port por demonstração se a query divergir muito) seguem a mesma forma de `BalancetePort`: recebem `enteId` + período, devolvem um agregado de leitura imutável (`BalancoOrcamentario`, `BalancoFinanceiro`, `BalancoPatrimonial`, `Dvp` — VOs no `razao-domain`, sem setter). O use case de leitura (`GerarDcasp*` ou um por demonstração, espelhando `GerarBalancete`) só exige `Acao.LER` — nunca MFA (mesma nota do `GerarBalancete`).
  - **Cada demonstração pós-encerramento reflete os lançamentos de encerramento do ADR-0045.** Como a apuração de resultado é sempre por fato novo (append-only), a demonstração de um período encerrado é automaticamente consistente assim que os lançamentos de encerramento forem commitados — não precisa de um passo de "publicação" separado do encerramento em si.
- **Consequências:** nenhuma tabela nova de "demonstração materializada" a manter sincronizada manualmente; a consistência é a mesma consistência do razão (forte dentro da transação; para portal/relatório fora do OLTP primário, dentro do SLA já definido pelo ADR-0007 — 1 dia útil). Custo: 4 queries potencialmente complexas (Balanço Orçamentário cruza dotação/empenhado/liquidado/pago; Balanço Patrimonial precisa do saldo por conta patrimonial; DVP precisa do detalhamento VPA/VPD) — escopo de implementação de cada uma fica para as issues filhas de `EncerrarExercicio`/DCASP, não fechado neste ADR.
- **Alternativas consideradas:**
  - **Gerar as demonstrações como parte do fato de encerramento (persistidas como snapshot no momento do fechamento)** — rejeitada nesta fase: acopla a demonstração ao momento exato do encerramento e duplica dado que já é derivável a qualquer momento do razão; um bug na query de leitura exigiria reprocessar/republicar snapshots em vez de só corrigir a query (perde a propriedade "read model reconstruível" do ADR-0007).
  - **Nova store de leitura dedicada (ex. tabela de projeção populada por trigger/CDC)** — rejeitada por enquanto: complexidade além do necessário no MVP (mesma alternativa já rejeitada pelo ADR-0007 para read models em geral); a query direta sobre o razão é suficiente até o volume justificar projeção materializada.
  - **Um único port genérico `DcaspPort` que devolve as 4 demonstrações de uma vez** — não decidido aqui (fica para a implementação): pode ser 1 port com 4 métodos ou 4 ports, dependendo de quanto as queries compartilham. Não é uma decisão de arquitetura, é detalhe de implementação.
