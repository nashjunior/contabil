# ADR-0052 · Fechar o fluxo completo pela UI: IdP de dev local, proxy Vite e esqueleto de telas de liquidação/pagamento/gate

- **Status:** Aceita
- **Data:** 2026-08-01
- **Contexto:** RAZ-221 (validação E2E RAZ-210, "a parte 'UI de verdade'") levantou 3 gaps que impedem operar o ciclo completo empenho→liquidação→pagamento→aprovação pela UI, mesmo com o backend correspondente já provado ponta a ponta via API:
  1. `AuthContext.entrar` (RAZ-120) fabrica um bearer opaco `dev.<cpf>.<ente>` — não é um JWT, `VerificadorJwtGovBr` rejeita. O único caminho de login real do SPA é `/sessao/oauth/iniciar` (ADR-0035), que depende do gov.br staging real — bloqueado hoje por ausência de cliente OIDC registrado ([runbook RAZ-126](../../operacao/RAZ-126-runbook-oidc-login-govbr.md), "Bloqueador externo"). Não existe, no repositório, nenhum IdP-stub **executável por HTTP** que um navegador possa alcançar — o único "stub" que existe hoje é a suíte e2e (`frontend/e2e/support/jwt.ts`, `AssinadorJwtE2e`), que assina localmente um JWT RS256 e o injeta *fora* da UI, direto no contexto do Playwright/chamadas HTTP (`frontend/e2e/specs/fluxo-execucao.pw.ts:31-33`, `frontend/e2e/support/apiExecucao.ts:12-14`), configurando o backend real via `GOVBR_IAM_ISSUER`/`GOVBR_IAM_AUDIENCE`/`GOVBR_IAM_PUBLIC_KEY_PEM` (`frontend/e2e/global-setup.ts:71-73`, consumidos por `VerificadorJwtGovBr`, que verifica qualquer JWT RS256 cujo emissor/audiência/assinatura batam com essa config — não chama o gov.br real).
  2. Só empenho tem tela (`features/execucao/pages/ExecucaoPage.tsx`). Liquidação, pagamento, o gate de aprovação 4-eyes e a trilha têm client (`shared/api/client.ts`) e controller reais, mas nenhuma rota/página — confirmado por grep (`Liquidacao|Pagamento|AprovacaoFila` em `frontend/src/features` e `AppRoutes.tsx`: zero ocorrências fora do client) e pelo próprio `frontend/README.md` §"Gaps sinalizados" itens 2/3. Adicionalmente, a decisão do gate em si (`POST /execucao/liquidacoes/{id}/aprovacao`, `LiquidacaoController.aprovar`, `bootstrap/.../escrita/LiquidacaoController.java:60-73`) **não tem client method nem schema OpenAPI** — só existe hardcoded no helper e2e (`apiExecucao.ts`), fora de `shared/api/client.ts`/`openapi/contrato-provisorio.yaml`. O contrato provisório já sinalizava isso (`contrato-provisorio.yaml:20-26`, comentário RAZ-188: "decisão do gate... follow-up").
  3. Cookie de sessão (`JSESSIONID` e `sessao-csrf`) é `Secure=true` (`application.yml:36-43`, `CsrfCookieSessaoLogin.java:24-31`) e o SPA não tem proxy de dev (`vite.config.ts` não tem `server.proxy`) nem um valor default de `CORS_ALLOWED_ORIGINS` (`CorsWebConfiguration.java` — desligado por padrão, correto por design) para `npm run dev` (`:5173`) falar com o backend (`:8080`) em desenvolvimento local sem fricção cross-origin.
- **Decisão:**
  1. **IdP de dev local, exposto por HTTP, dono backend.** Estender a mecânica já provada e seguraníssima da suíte e2e para um endpoint real: um controller `bootstrap` **restrito ao caminho de login por cabeçalho já existente** (não reimplementa o BFF/cookie do ADR-0035), ativo **só** quando o backend roda com um par de chaves de dev configurado via `GOVBR_IAM_*` (mesma env var que o e2e já usa) **e** uma flag explícita adicional (ex.: `SIAFIC_DEV_IDP_ENABLED=true`) — nunca ativo por acidente em staging/produção, onde `GOVBR_IAM_*` aponta para a chave pública real do gov.br e a assinatura de qualquer JWT local falharia de qualquer forma. O endpoint recebe `{cpf, enteId, papel}`, assina um JWT RS256 com a chave **privada** de dev (que só existe no processo backend, nunca no bundle do navegador) e devolve `{bearerToken}`. O SPA (`LoginPage`, formulário "Modo desenvolvimento") passa a chamar esse endpoint em vez de fabricar a string `dev.<cpf>.<ente>|` — o restante do caminho (`AuthContext.entrar` grava `bearerToken`, `client.ts` já sabe usar `Authorization: Bearer` quando presente) **não muda**, porque `SessaoAutenticadaHttpResolver` já verifica qualquer bearer via `ServicoIdentidade`, real ou de dev, da mesma forma. Implementação (Java) é **fora da fronteira deste ADR de frontend** — abre issue-filha de backend (ver disposição da RAZ-221).
  2. **Proxy Vite para dev local.** `vite.config.ts` ganha `server.proxy` para `/api` e `/sessao` apontando para `http://localhost:8080` (`changeOrigin: true`). Isso torna SPA e API mesma origem do ponto de vista do navegador (`http://localhost:5173`), então o cookie `Secure` do BFF de login (ADR-0035) e o cookie CSRF trafegam normalmente em HTTP local sem exigir HTTPS nem abrir `CORS_ALLOWED_ORIGINS` — que continua desligado por padrão (design correto do `CorsWebConfiguration`) e serve só o caso cross-origin real (preview/E2E em porta diferente, como já faz `frontend/e2e/global-setup.ts:74`).
  3. **Esqueleto de telas, não as telas.** Novas rotas/páginas para Liquidação, Pagamento e Fila de Aprovação (com trilha) seguem a MESMA camada já estabelecida (ADR-0032 monólito modular por feature, ADR-0041 hook fino + `application/` puro): `pages/ → components/ → api/ (hook React Query) → application/ (caso de uso puro nomeado igual ao real do backend) → shared/api/client.ts`. Vivem em `features/execucao/` (mesma feature do empenho — mesmo controller/domínio, ADR-0032 já cobre isso pelas fronteiras dos 6+ controllers reais). O client ganha o método que faltava: `aprovarLiquidacao` (`POST /execucao/liquidacoes/{id}/aprovacao`, tipos `AprovacaoRequest`/reusa `LiquidacaoResponse`), com o path/schema correspondente adicionado a `openapi/contrato-provisorio.yaml` (convenção já existente: quem adiciona client method adiciona o contrato). O escopo desta entrega é o esqueleto (rotas montadas, páginas compiláveis, fila de aprovação já lendo dado real via `consultarFilaAprovacao`) — os formulários de registro (liquidação/pagamento, no padrão RHF+zod do ADR-0043) e a ação de decisão do gate ficam para issue-filha de implementação de tela (dono: Bruno).
- **Consequências:** Nenhuma mudança na fronteira domínio/borda do backend além do endpoint de dev-IdP (que é puramente de infraestrutura de teste, não de negócio). O caminho de produção do login (ADR-0035, OAuth real) não muda. O client de API ganha 1 método novo e o contrato ganha 1 path novo, sem alterar nenhum contrato existente. O proxy Vite é dev-only (`vite.config.ts` só afeta `npm run dev`; build de produção não usa `server.proxy`). O dev-IdP fica com uma dependência explícita de configuração (2 flags) para reduzir o raio de um vazamento acidental — mesmo assim, deve ser tratado como *não pronto para produção* por natureza (é literalmente uma chave privada de assinatura de identidade rodando no processo), então a issue-filha de backend deve registrar esse endpoint com o mesmo cuidado de fail-closed que `ServicoIdentidadeIndisponivel`/`SessaoLoginGovBrOAuthProperties` já usam para outros gaps operacionais.
- **Alternativas consideradas:**
  1. **SPA assina o JWT no navegador** (o form de dev já faz algo parecido hoje, só que com uma string opaca) — rejeitada: exigiria a chave **privada** de assinatura no bundle JS, alcançável por qualquer script na página; contraria a mesma invariante que o ADR-0035 já usa para rejeitar "SPA guarda a asserção real" (exfiltração via XSS, LGPD). Corrigir isso significa mover a assinatura para o único lugar que já é confiável para segredos: o processo backend.
  2. **Não mexer no proxy, e só documentar `CORS_ALLOWED_ORIGINS=http://localhost:5173` como variável de ambiente de dev** — considerada e parcialmente incorporada (fica documentada como alternativa para quem preferir rodar cross-origin, ex. testar o app já "buildado"), mas o proxy é a opção default porque também resolve o problema do cookie `Secure` em HTTP puro sem depender de nenhuma flag de ambiente do lado do backend — funciona com a config de cookie/CORS de produção inalterada.
  3. **Construir as 3 telas completas nesta mesma entrega** — rejeitada por escopo: telas com formulário (RHF+zod, ADR-0043) e a UX do gate de aprovação (ação irreversível, 4-eyes) merecem revisão de design/UX própria (Paula) e não são decisão de arquitetura — cabem na issue-filha de implementação, não neste ADR.
