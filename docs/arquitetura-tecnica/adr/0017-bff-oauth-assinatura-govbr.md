# ADR-0017 · BFF OAuth2 do signatário para Assinatura gov.br

- **Status:** Aceita
- **Data:** 2026-07-19
- **Contexto:** A assinatura gov.br avançada (ADR-0008, RAZ-11) já possui o adapter HTTP real para `assinarPKCS7`, mas ele recebe o token OAuth2 do signatário por `Supplier<String>`. Faltava a superfície web/BFF que conduz o fluxo `authorization_code` interativo contra o gov.br (`cas.staging.iti.br/oauth2.0/authorize`) e entrega um token de usuário ao adapter. O projeto usa Spring Boot no `bootstrap` como composition root (ADR-0012) e a borda HTTP não deve entrar nos módulos puros de domínio/application (ADR-0002). Tenant efetivo continua vindo de contrato verificado e RLS (ADR-0003); a assinatura do documento carrega `ente` explicitamente (ADR-0015).
- **Decisão:** O BFF web de assinatura fica no módulo `bootstrap`, como borda HTTP da aplicação executável. O fluxo usa Spring MVC, `HttpSession` server-side e PKCE: `GET /assinatura/oauth/iniciar` cria `state` e `code_verifier`, associa-os ao `ente` verificado da sessão autenticada, e redireciona para o authorization endpoint gov.br com escopos `sign` e `signature_session`. `GET /assinatura/oauth/callback` valida o `state` na sessão, troca `code` por `access_token` no token endpoint configurado, autentica a asserção gov.br pelo port `ServicoIdentidade`, confere que o `ente` retornado pelo IAM é igual ao `ente` do fluxo pendente, grava a `ServicoIdentidade.Sessao` verificada no `HttpSession` e só então grava o token da assinatura. O `Supplier<String>` injetável lê o token da sessão HTTP corrente e falha fechado se não houver token válido.
- **Consequências:** O código de domínio e o adapter `ProvedorAssinaturaGovBrHttp` não conhecem Spring MVC nem sessão web. A proteção CSRF do OAuth fica em `state` server-side, e o `code_verifier` nunca sai da sessão. Credenciais (`client_id`/`client_secret`) entram por ambiente/cofre; sem elas o endpoint falha fechado no início do fluxo, preservando o startup local. A identidade nominal do signatário e o tenant não são aceitos por header/query/body cru: devem vir do IAM gov.br/ICP-Brasil; o resolvedor padrão lê `ServicoIdentidade.Sessao` do `HttpSession` e falha fechado se a sessão estiver ausente, expirada ou sem MFA concluído. Este BFF armazena server-side o token OAuth da assinatura, o `ente` de escopo do fluxo e a sessão IAM verificada retornada pelo port de identidade; divergência de tenant no callback é recusada antes de trocar a sessão ou expor o token ao supplier. Teste ponta-a-ponta real segue bloqueado até haver aplicação OAuth2 registrada no gov.br staging, mas a mecânica redirect/callback/token/IAM é testável com stub local.
- **Alternativas consideradas:** Colocar controller em `plataforma-infra` (rejeitado: mistura adapter transversal com composition root HTTP); fluxo stateless com `state` assinado contendo `code_verifier` (rejeitado para F0: aumenta superfície criptográfica/segredo na borda sem necessidade enquanto `HttpSession` atende ao BFF); passar token diretamente por parâmetro para o serviço de assinatura (rejeitado: vazaria token para contratos de domínio/application e quebraria o seam já definido por RAZ-11).
