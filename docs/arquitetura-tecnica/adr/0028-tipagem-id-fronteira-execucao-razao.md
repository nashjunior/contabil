# ADR-0028 · Tipagem de id na fronteira execução↔razão: VO local do consumidor, UUID contido no adapter, id de domínio não sobe ao shared kernel

- **Status:** Aceita
- **Data:** 2026-07-26
- **Contexto:** RAZ-106 avaliou tipar o id do fato contábil na fronteira execução↔razão. Hoje os ports de escrituração da execução — `ExecucaoContabilPort.registrarEmpenho/registrarLiquidacao/registrarPagamento` — devolvem `UUID` cru; o `RegistrarEmpenho` guarda esse `UUID` no agregado `Empenho` (`private final UUID fatoContabilId`) e o `ExecucaoContabilPortAdapter` (bootstrap) faz `fato.id().valor()` para produzi-lo. Por decisão deliberada, `execucao-domain` **não** depende de `razao-domain` — `execucao-domain/build.gradle.kts` só declara `plataforma-domain` no classpath, então importar `FatoContabilId` (id do agregado do razão) seria **erro de compilação** (parede primária), reforçado em bytecode pelo ArchUnit `modulos_de_negocio_sao_livres_de_ciclo` (defesa em profundidade); ver também o javadoc de `ExecucaoContabilPort`. Ao mesmo tempo, RAZ-93 fechou o UUID cru em `execucao-domain` (`EmpenhoId`, `DotacaoId`, `CredorId`, `UnidadeGestoraId`, `ContratoId`) e o razão já tipa **todos** os seus ids — agregado (`FatoContabilId`), entidade local (`LancamentoId`) e referência (`ContaContabilId`). O `UUID fatoContabilId` no `Empenho` ficou como o **último buraco de primitive obsession** do domínio de execução, confundível com qualquer outro id. Nota: a premissa do brief de que `Lancamento.id`/`contaId` seguem UUID cru está **desatualizada** — ambos já são VOs (`LancamentoId`/`ContaContabilId`).
- **Decisão:**
  1. **Id de agregado raiz e id de entidade local são VO tipado no módulo que os possui.** Já é a realidade: razão (`FatoContabilId`, `LancamentoId`, `ContaContabilId`), execução (`EmpenhoId`, `LiquidacaoId`, `PagamentoId`, `DotacaoId`, …). Não há "raiz tipa, local/cross-ref não": tipa-se tudo, cada id no seu módulo dono.
  2. **Referência cross-módulo (execução guardando o id de um fato do razão) é modelada por um VO de referência do módulo CONSUMIDOR** — `br.contabil.execucao.domain.ReferenciaFatoContabil` — e **nunca** importando `razao.domain.FatoContabilId` (não está no classpath de `execucao-domain` — seria erro de compilação; e acoplaria execução→razão). É o padrão *reference by identity* entre módulos: cada lado nomeia a referência na sua própria linguagem.
  3. **`plataforma-domain` (shared kernel) NÃO recebe id de agregado de módulo de negócio.** Ele guarda só VOs genuinamente transversais de plataforma (`TenantId`, `Dinheiro`, `ChaveIdempotencia`). Um id de agregado é linguagem ubíqua do módulo dono; subir `FatoContabilId` ao kernel vazaria o razão para todos os módulos e abriria precedente para acumular todo id cross-referenciado (ex.: `EmpenhoId` quando o razão precisar referenciar um empenho). Coerente com [ADR-0025](./0025-building-blocks-taticos-ddd.md) §3 (rejeita hierarquia genérica `Identifier`) e com o critério de shared kernel do [ADR-0014](./0014-contratos-plataforma-ports.md).
  4. **O primitivo de serialização que cruza o seam é `UUID`, mas fica CONTIDO no adapter de tradução.** O port `ExecucaoContabilPort` (que vive em `execucao-domain`) passa a devolver `ReferenciaFatoContabil` nos três métodos. O `UUID` só aparece dentro do `ExecucaoContabilPortAdapter` (bootstrap/composition root — a única classe que conhece os dois módulos), que faz `new ReferenciaFatoContabil(fato.id().valor())`. Resultado: zero acoplamento execução→razão (o adapter, não o `execucao-domain`, conhece `FatoContabilId`); o `Empenho` deixa de ter `UUID` cru; o `UUID` fica só na borda de tradução — honesto como primitivo de fio, sem contaminar o domínio.
- **Consequências:**
  - O `Empenho` passa a guardar `ReferenciaFatoContabil` (não `UUID`); a auditoria loga `referencia.valor().toString()`.
  - Persistência (colunas `uuid` em banco) e o roteiro de contabilização não mudam — só a fronteira de tipos em memória.
  - Escopo de implementação (mecânico, follow-up): definir `ReferenciaFatoContabil` em `execucao-domain`; alterar os 3 métodos do port; trocar o campo/getter do `Empenho`; propagar em `RegistrarEmpenho`; traduzir no adapter; ajustar testes (`EmpenhoTest`, `RegistrarEmpenhoTest`, testes do adapter).
  - **Gate de execução:** a implementação toca `Empenho.java`, `ExecucaoContabilPort.java`, `RegistrarEmpenho.java`, o adapter e seus testes — os **mesmos** arquivos do changeset em voo de empenho↔assinatura (RAZ-98/[ADR-0027](./0027-wiring-empenho-assinatura-gate-interativo.md)) hoje no working tree. Fazer a refatoração só **depois** desse changeset commitar, para não entangle/misturar commits (é o "não fazer durante refatoração concorrente da execução" do brief). Delegado a issue filha.
- **Alternativas consideradas:**
  - **Mover `FatoContabilId` para `plataforma-domain` e o port devolvê-lo.** Rejeitada: sobe id de agregado do razão ao shared kernel, vaza a linguagem do razão para todos os módulos e cria precedente de acúmulo de ids cross-referenciados no kernel; contraria o espírito de [ADR-0025](./0025-building-blocks-taticos-ddd.md) §3 e [ADR-0014](./0014-contratos-plataforma-ports.md).
  - **Manter `UUID` cru em todo lugar (status quo).** Rejeitada: deixa o único buraco de primitive obsession no `Empenho` pós-RAZ-93; `UUID fatoContabilId` é confundível com qualquer outro id do agregado.
  - **Port devolve `UUID`, mas o `Empenho` embrulha em `ReferenciaFatoContabil`.** Viável, mas inconsistente: deixa o primitivo cru na superfície do port sem ganho, já que o VO é do próprio execução (nada impede o port devolvê-lo). A variante escolhida devolve o VO do port e contém o `UUID` no adapter, para type-safety ponta a ponta no domínio.
