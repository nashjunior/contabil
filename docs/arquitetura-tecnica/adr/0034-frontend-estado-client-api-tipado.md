# ADR-0034 · Frontend: estado (React Query) e client de API tipado contra os controllers reais

- **Status:** Aceita
- **Data:** 2026-07-26
- **Contexto:** RAZ-119 pede client de API tipado **derivado dos controllers reais** (`bootstrap/**/*Controller.java`), não de suposição. Li o código real antes de decidir — diferente da constatação de uma execução anterior sobre um snapshot desatualizado (sem controllers), o `master` atual **tem** 7 controllers reais: `EmpenhoController`, `LiquidacaoController`, `PagamentoController` (`br.contabil.escrita`, RAZ-105), `RazaoConsultaController`, `ExecucaoConsultaController`, `CatalogoContasController` (`br.contabil.consulta`, RAZ-101/114/115/117), `AssinaturaEmpenhoController`/`AssinaturaGovBrOAuthController` (`br.contabil.assinatura`, fora do escopo do client desta ADR — fluxo BFF OAuth2 próprio). O contrato de leitura/escrita já converge para RAZ-79 §6.1 via [ADR-0030](./0030-contrato-consultas-razao-convergencia-79.md) e [ADR-0029](./0029-contrato-leitura-fila-aprovacao-trilha.md): envelope de erro único, dinheiro string, `mfa_requerido`→428. Não existe springdoc-openapi no build (`grep` em `build.gradle.kts`/`gradle/libs.versions.toml` não acha `springdoc`) — sem endpoint `/v3/api-docs` para gerar tipos automaticamente hoje.
- **Decisão:**
  1. **Contrato real, lido diretamente do código, não de suposição.** Transcrevi os 7 controllers (rotas, `record`s de request/response, exceptions mapeadas) para `frontend/openapi/contrato-real.yaml` (OpenAPI 3), com cada `operationId`/schema anotado com o arquivo/linha Java de origem. Client TS (`frontend/src/shared/api/generated/schema.d.ts`) é gerado deste YAML via `openapi-typescript` (`npm run api:generate`) — **nenhum tipo escrito à mão diretamente**; o YAML é o único artefato hand-maintained, e ele documenta a proveniência de cada campo.
  2. **Ente é path segment, não header.** Toda rota real é `/api/v1/entes/{enteId}/...` (não um header `X-Tenant-Id` inventado) — o client (`shared/api/client.ts`) constrói a URL com o `enteId` ativo (`useEnte()`, nome `ente`/`enteId` — convenção da casa, [ADR-0015](./0015-atribuicao-tenant-explicita-no-contrato.md), não `tenant`/`tenantId`).
  3. **Auth: `Authorization: Bearer <asserção gov.br>`, stateless, por request** — mesmo mecanismo de `SessaoAutenticadaHttpResolver` (`br.contabil.consulta`), usado por todos os 6 controllers de execução/consulta. O client injeta o header a partir de um token de sessão obtido no login gov.br (BFF OAuth2, `AssinaturaGovBrOAuthController` — fluxo de assinatura; o login "de app" ainda não tem controller dedicado fora do fluxo de assinatura, gap sinalizado no comentário da RAZ-119, não resolvido aqui). Nenhuma chamada de API sai sem esse header — erro em tempo de dev se o token não estiver setado.
  4. **Dinheiro é sempre string decimal**, nunca `number` — `Dinheiro.valor().toPlainString()` na resposta ([ADR-0006](./0006-dinheiro-decimal.md), reforçado pelo `DinheiroJacksonModule` + [ADR-0030](./0030-contrato-consultas-razao-convergencia-79.md) §2). Tipo `Dinheiro` do client é `string` fixado (override no OpenAPI, já que `type: string` nativo já cobre — sem ambiguidade de `number`), formatado só na borda de exibição, nunca em aritmética client-side.
  5. **PII (CPF do beneficiário) chega mascarada por padrão** — `PagamentoController.BeneficiarioResponse.cpfCnpj` já vem de `new Cpf(...).mascarado()` no servidor (RAZ-79 §6.1: "toda resposta que inclui `beneficiario.cpfCnpj` vem mascarada por padrão"). Client trata como opaco, nunca tenta desmascarar; ver RAZ-100 §2 componente 3 (CPF Mascarado) — "Integral" é capability separada (`execucao:beneficiario:ler_integral`), fora do escopo deste client v1.
  6. **Envelope de erro único `{codigo, mensagem, detalhes}`** ([ADR-0030](./0030-contrato-consultas-razao-convergencia-79.md) §3) mapeado para uma classe `ApiError` só no cliente — `codigo` decide UI (ex.: `saldo_insuficiente` → erro inline no campo; `mfa_requerido`/428 → fluxo de elevação de MFA; `conta_nao_encontrada`/404, `periodo_encerrado`/409, `liquidacao_ja_decidida`/409). Nenhuma segunda taxonomia de erro no front.
  7. **Paginação por cursor opaco** (`{itens, proximoCursor}`) nas listas reais — fila de aprovação (`GET .../execucao/liquidacoes`) e catálogo PCASP (`GET .../razao/contas`) — hook de feature encapsula o cursor, página nunca manipula string de cursor diretamente. Balancete **não** pagina ([ADR-0030](./0030-contrato-consultas-razao-convergencia-79.md) §4 — é demonstrativo).
  8. **Lote de pagamento é fail-soft `207`** (`POST .../pagamentos:lote`) — `LotePagamentoResponse{processados, errors}` sempre retorna `200`-like sucesso parcial, nunca lança por item ruim; hook de mutation devolve os dois arrays, UI materializa "Resumo Fail-soft" (RAZ-100 §2 componente 10), nunca trata `207` como erro genérico.
  9. **Estado: React Query para todo server-state; estado global mínimo** (ente ativo, sessão gov.br, tema — nada mais). Hook por feature (`useEmpenho`, `useFilaAprovacao`, `useRegistrarPagamentoLote`) encapsula query/mutation + `queryKey`; mutation de escrita invalida a `queryKey` de consulta afetada no `onSuccess` (ex.: registrar liquidação invalida a fila de aprovação).
- **Consequências:**
  - **+** Tipos batem com o contrato real na data desta ADR — verificável por qualquer um lendo os 7 controllers citados.
  - **+** `ente`/`enteId` e envelope de erro consistentes com a convenção já ratificada (ADR-0015/ADR-0030) — sem reinventar contrato.
  - **−** `contrato-real.yaml` é **hand-maintained**: se um controller mudar sem alguém atualizar o YAML, o client tipado diverge silenciosamente — exatamente o risco que motivou a leitura de código desta ADR em vez de assumir "pronto". Mitigação: **springdoc-openapi como fast-follow** (dependência Gradle + `/v3/api-docs`) elimina esse hand-maintenance — sinalizado como issue-filha no comentário da RAZ-119 (dono: backend), não bloqueia este scaffold.
  - **−** Login "de app" (fora do fluxo de assinatura) não tem controller — o client tem um ponto de injeção de token, mas o fluxo real de obtenção do token gov.br para uso geral (não só assinatura) é gap sinalizado, não resolvido aqui.
- **Alternativas consideradas:** Adicionar springdoc-openapi agora, nesta mesma execução (rejeitada — `build.gradle.kts`/`bootstrap` têm risco de conflito com trabalho em andamento de outro agente no mesmo `master` neste momento; mudança de build compartilhado fica para issue-filha própria, revisada isoladamente); assumir contrato a partir só da documentação (`fluxo-execucao-operador-contrato-api.md`) sem ler os `.java` (rejeitada — é exatamente o erro que a persona deste agente foi avisada que já aconteceu; a doc pode estar desatualizada em relação ao código, como o próprio [ADR-0030](./0030-contrato-consultas-razao-convergencia-79.md) documentou ter acontecido uma vez).
