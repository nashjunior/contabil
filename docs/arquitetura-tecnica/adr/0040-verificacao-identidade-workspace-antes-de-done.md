# ADR-0040 · Verificação de identidade do workspace antes de iniciar trabalho e antes de declarar `done`

- **Status:** Aceita
- **Data:** 2026-08-01
- **Contexto:** O workspace por-agente provisionado pelo harness Paperclip (`/Users/.../.paperclip/instances/default/workspaces/<agentId>/`) já foi observado em dois estados incorretos, ambos silenciosos — nenhum sinal de erro avisa o agente:
  1. **Vazio, sem `.git`** (reproduzido ao vivo nesta sessão, RAZ-166, 2026-08-01): o agente precisa descobrir por conta própria que o repo autoritativo vive em outro caminho (`codebase.effectiveLocalFolder`, via API de projetos).
  2. **Cópia estática desconectada, com `.git` próprio** (RAZ-122/139/163, 2026-07-26/27): o workspace foi provisionado uma vez como snapshot do repo real, nunca mais sincronizou, mas **aceita commits normalmente** — por ter git log e HEAD válidos, *parece* um clone funcional. Um agente commitou ali, marcou `done` com evidência (testes passando) aparentemente sólida, e o código nunca chegou ao repo real. O mesmo erro se repetiu numa execução *concorrente* da mesma identidade de agente, que reabriu a issue de reentrega como `done` com um achado falso ("componente já existe") porque checou a cópia errada.

  Já são **8 issues** no board tratando sintomas desse padrão (RAZ-70, 58, 43, 41, 86, 164, 163, 166) sem que nenhuma ataque a causa raiz. Cada ocorrência consome um ciclo inteiro de outro agente para descobrir, investigar e reentregar. Não é decisão de arquitetura de **produto**: é de **processo/tooling de agentes**, mesma categoria do ADR-0037 (mas um sintoma anterior/mais básico: ADR-0037 assume que o agente já está no repo real e disputa índice com outros agentes; aqui o problema é o agente não estar no repo real *de jeito nenhum*, e nada acusar isso).
- **Decisão:** Verificação de identidade do workspace **obrigatória e barata**, em dois pontos do ciclo de vida de qualquer tarefa:
  1. **Antes de iniciar trabalho** (qualquer edição/criação de arquivo): resolver o caminho autoritativo via `GET /api/companies/{companyId}/projects` → `codebase.effectiveLocalFolder`. Se o `pwd`/diretório de trabalho atual não for esse caminho (nem um `git worktree` derivado dele — `git worktree list` a partir do caminho autoritativo), o agente **entra no caminho autoritativo** (ou cria/usa um worktree próprio dele, conforme ADR-0037) antes de tocar em qualquer arquivo. Nunca assumir que um diretório com `.git` funcional é o repo certo só porque `git log`/`git status` respondem normalmente — isso é exatamente o sintoma da cópia desconectada.
  2. **Antes de declarar `done`** em qualquer issue com deliverable de código: confirmar que o commit existe **no caminho autoritativo**, não apenas no `.git` do cwd — `git -C "<effectiveLocalFolder>" log --oneline -3 -- <arquivos alterados>` (ou `git show HEAD:<path>` a partir do caminho autoritativo). Só then marcar `done`. Isso é a mesma disciplina já registrada em [[feedback_verify_before_propagating_findings]] (memória de agente), agora como convenção de repositório — não depende de nenhum agente lembrar por conta própria.
  3. **Fora do escopo desta ADR (ação de plataforma, não de repo):** o fato do harness provisionar o workspace por-agente como cópia estática ao invés de clone/worktree real, e não emitir nenhum sinal de erro quando desconectado, é um defeito de provisionamento do Paperclip — não corrigível por convenção de AGENTS.md/ADR. Fica registrado como pendência para o operador humano da plataforma (ver issue-filha de RAZ-166): (a) provisionar o workspace de cada agente como clone/worktree real do repo autoritativo, e/ou (b) expor uma verificação barata e nativa do harness (ex.: comparar `git rev-parse HEAD` do workspace do agente contra o caminho autoritativo) que falhe alto e cedo antes do agente sequer começar.
- **Consequências:** custo de uma chamada de API + um `git log`/`git show` a mais por tarefa — desprezível perto de "um ciclo inteiro de outro agente" que cada recorrência já custou. Cobre os dois sintomas observados (workspace vazio e cópia desconectada), porque ambos são detectados pela mesma pergunta ("o commit existe no caminho que a API de projetos diz ser o autoritativo?"), sem depender de nenhum sinal do próprio `.git` do agente (que é exatamente o que engana nos dois casos). Não resolve a causa raiz de provisionamento — é mitigação de camada de convenção, como as camadas 1-2 do ADR-0037, e supõe boa-fé/disciplina do agente (não é enforced automaticamente; ver alternativas rejeitadas abaixo).
- **Alternativas consideradas:**
  - **Hook git (`commit-msg`/`pre-commit`) que faz a checagem automaticamente:** rejeitado por ora — exigiria chamar a API do Paperclip (rede, env vars `PAPERCLIP_API_URL`/`PAPERCLIP_COMPANY_ID`) de dentro de um hook git, o que quebra em qualquer commit humano local ou ambiente sem essas variáveis, e adiciona uma dependência de rede a um hook que hoje é 100% local (ADR-0037). Diferente do commit-msg da ADR-0037 (que só olha `git diff --cached`, sempre disponível), este hook não teria como funcionar sem a API do harness — que é justamente a camada de infra que não está sob controle deste repo.
  - **Confiar em variável de ambiente `PAPERCLIP_CANONICAL_REPO_PATH`:** essa variável não existe hoje (checado nesta sessão — o env do agente só expõe `PAPERCLIP_WORKSPACE_CWD`/`AGENT_HOME`, que **são** o caminho potencialmente desconectado, não uma referência independente). Fica registrada como a mitigação de plataforma preferível no item 3, mas não pode ser a convenção *hoje* porque não há a variável para checar.
  - **Confiar em "tem `.git` com log válido" como sinal de repo correto:** rejeitado — é exatamente o sinal que enganou em RAZ-122/139/163; a cópia desconectada tem `.git` e log válidos.
  - **Não fazer nada e esperar o operador de plataforma corrigir o provisionamento:** rejeitado — já são 8 issues e o padrão demonstrou se automanter mesmo depois de "corrigido" (RAZ-163 foi fechado incorretamente de novo por uma execução concorrente); a mitigação de convenção é barata e reduz recorrência **imediatamente**, independente de quando/se a infra for corrigida.
