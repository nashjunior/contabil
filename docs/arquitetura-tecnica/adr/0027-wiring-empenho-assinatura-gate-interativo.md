# ADR-0027 · Wiring RegistrarEmpenho → assinatura: gate interativo pós-outbox de documento, não worker autônomo

- **Status:** Proposta
- **Data:** 2026-07-26
- **Contexto:** RAZ-74 (achado do RAZ-68) constatou que o pipeline de assinatura eletrônica (RAZ-11/24/28/29/31/34 — OAuth2 gov.br + PAdES/PDFBox + OCSP/CRL + object store + trilha) está pronto e testado isoladamente, mas nenhum caso de uso de negócio o aciona (`grep ServicoAssinatura` em `razao/`+`execucao/` não retorna nada). `RegistrarEmpenho` (execucao-application) é o candidato natural — a nota de empenho é o exemplo citado em [transversais/01-assinatura-eletronica.md §Fluxo](../../transversais/01-assinatura-eletronica.md#fluxo--assinar-uma-nota-de-empenho) — mas hoje só valida RBAC, checa saldo, escritura o fato no razão, persiste o `Empenho` e publica transparência; não gera PDF/A nem chama `ServicoAssinatura`. RAZ-98 identificou 4 lacunas que bloqueiam um patch direto: (1) onde no ciclo de vida do empenho a assinatura é disparada, sem violar "efeito externo só via outbox, nunca síncrono na transação do fato" ([ADR-0004](./0004-outbox-idempotente.md)/[ADR-0011](./0011-idempotencia-ponta-a-ponta.md)); (2) não existe gerador de PDF/A da nota de empenho a partir do agregado `Empenho`; (3) a assinatura avançada gov.br exige token OAuth2 de uma sessão interativa do **signatário** (fluxo já modelado em `AssinaturaGovBrOAuthController`/RAZ-28/29, escopo `HttpSession`), que não coincide necessariamente com quem invoca `RegistrarEmpenho`; (4) falta a parametrização do nível exigido por ente × tipo de documento (item 5 do transversal 01).
- **Decisão:**
  - **(a) Dois estágios distintos, não um só.** `RegistrarEmpenho.executar()` ganha **um** passo adicional, na mesma transação do fato: publicar no outbox (via novo port `SolicitacaoDocumentoAssinaturaPort`, mesma forma de `PublicacaoTransparenciaExecucaoPort`) um evento `execucao_empenho_pendente_documento`. Isso **não viola** o ADR-0004: gravar uma linha de outbox é escrita local no mesmo banco/transação, não é a chamada externa que o ADR proíbe — é exatamente o mecanismo que o ADR-0004 prescreve para desacoplar o que vem depois.
  - **(b) Geração do PDF/A é assíncrona, via worker.** Um novo consumidor (`EmpenhoDocumentoPendenteWorker`, mesma forma de `OutboxEntregaWorker`) processa esse evento **fora** da transação do fato: gera o PDF/A a partir do `Empenho` (novo port `GeradorNotaEmpenhoPdf` em `execucao-domain`, implementado com PDFBox em `execucao-infra` — mesma biblioteca já usada por `PreparadorAssinaturaPades`/RAZ-34, mas para o conteúdo do documento, não para o placeholder de assinatura), publica no object store via `ArmazenamentoDocumentos` ([ADR-0009](./0009-documentos-object-store.md)), e transiciona `Empenho` para `PENDENTE_ASSINATURA`, gravando a referência do documento pendente. Idempotente pela chave do outbox ([ADR-0011](./0011-idempotencia-ponta-a-ponta.md)) — reprocessar o mesmo evento não gera um segundo PDF.
  - **(c) A assinatura em si NÃO é outbox nem worker autônomo — é ação interativa e síncrona do ordenador.** Isto resolve o ponto (3) do contexto de forma decisiva: `ServicoAssinaturaGovBrAvancada` depende, através do provedor, de um token OAuth2 de escopo `sign`/`signature_session` obtido pela sessão HTTP do **próprio signatário** (`AssinaturaGovBrOAuthController`, RAZ-28/29). Um worker de fundo não tem — e não deve ter — esse token: guardar um token de assinatura para replay não-atendido por um processo automatizado comprometeria o não-repúdio (a assinatura deixaria de refletir um ato contemporâneo do signatário, contrariando a base legal do transversal 01 — MP 2.200-2/2001, Lei 14.063/2020). Por isso, novo caso de uso `AssinarEmpenho` (`execucao-application`), exposto em `POST /entes/{enteId}/execucao/empenhos/{id}/assinatura`, executado na requisição do ordenador **já autenticado** via o fluxo OAuth existente: exige `Acao.ASSINAR` sobre `execucao:empenho` (novo verbo RBAC, MFA por [ADR-0016](./0016-controle-acesso-mfa-movimentacao-recurso.md)); monta o `DocumentoParaAssinar` a partir da referência pendente; resolve o `NivelAssinatura` exigido (item d); chama `ServicoAssinatura.assinar(...)` **sincronamente**, dentro do escopo dessa própria chamada HTTP — isso não é a transação Σ=Σ do razão (que já foi commitada em `RegistrarEmpenho`), é uma ação de negócio distinta e interativa, da mesma natureza do callback OAuth que já existe; persiste `DOCUMENTO_ASSINADO` com FK ao `Empenho`; transiciona `Empenho` para `ASSINADO`; grava trilha.
  - **(d) Estado forte no agregado, mesmo padrão já decidido para Liquidação no ADR-0023.** `Empenho` ganha `status` (`REGISTRADO → PENDENTE_ASSINATURA → ASSINADO`, mais um terminal de retrabalho, `ASSINATURA_REJEITADA`, para reentrada manual), transicionado só pelas ações de domínio acima — nunca por setter direto. `Empenho` continua imutável (reconstrução via repositório); `EmpenhoRepository` (hoje só `inserir`/`buscarPorId`) ganha um método de atualização de estado/referência de documento.
  - **(e) Parametrização de nível por ente × tipo de documento (item 4 do transversal 01).** Novo port mínimo, `NivelAssinaturaExigidoPort.nivelExigido(TenantId ente, String tipoDocumento) -> NivelAssinatura`, com default `AVANCADA_GOVBR` (único nível suportado em F0) quando não configurado. Este ADR decide só a forma do port; a UI/tabela de administração de parametrização por ente é issue própria, fora deste escopo.
- **Consequências:** Habilita o primeiro caso de uso real do pipeline de assinatura, fechando o achado RAZ-74/RAZ-68. Trabalho novo de implementação: `SolicitacaoDocumentoAssinaturaPort` + `EmpenhoDocumentoPendenteWorker`, `GeradorNotaEmpenhoPdf` (domínio + infra PDFBox), `AssinarEmpenho` + endpoint, novo verbo RBAC `ASSINAR`, estado forte no `Empenho` + método de update no repositório, `NivelAssinaturaExigidoPort`. Uma nota de empenho registrada mas ainda não assinada é um estado de negócio real e visível — este ADR **não decide** se o empenho é vinculante/executável antes de assinado (ex.: pode a liquidação referenciar um empenho `PENDENTE_ASSINATURA`?); essa é uma questão de produto/regra de negócio (toca Lei 4.320/1964) que fica em aberto para decisão separada antes de `AssinarEmpenho` ir a produção — recomendo tratá-la como bloqueio explícito de uma issue de produto, não travar esta decisão de wiring técnico por ela. Não cobre workflow multi-assinatura nem ICP-Brasil qualificada (F1) — só o F0 avançada gov.br single-signer já implementado. Correção de nota já assinada segue estorno + novo documento (já documentado no transversal 01), não é tratada por este ADR.
- **Alternativas consideradas:**
  - **Worker de outbox chama `ServicoAssinaturaGovBrAvancada.assinar()` diretamente**, guardando um token OAuth do ordenador para reuso posterior pelo worker (literalmente o desenho sugerido em texto pela issue-mãe RAZ-98) — rejeitada: comprometeria o não-repúdio (assinatura sem ato contemporâneo do signatário) e exigiria guardar credencial de assinatura fora do fluxo interativo já desenhado (RAZ-28/29), abrindo superfície de abuso (replay de token por processo não atendido, sem o signatário saber).
  - **Assinatura inline dentro da própria transação de `RegistrarEmpenho`**, bloqueando o lançador até completar o round-trip gov.br — rejeitada: viola ADR-0004/ADR-0011 diretamente (chamada de rede real dentro da transação Σ=Σ do razão) e acopla a disponibilidade do gov.br à escrituração contábil.
  - **Não separar o estágio de documento/assinatura do estágio de registro do fato** (assinar como parte do mesmo ato de quem lança o empenho) — rejeitada: o ordenador que assina nem sempre é quem lança o empenho (mesma tensão de segregação já tratada para pagamento no [ADR-0023](./0023-gate-aprovacao-pagamento-segregacao.md)); manter dois atos distintos permite que sejam pessoas diferentes sem forçar um workflow síncrono bloqueante no lançamento.
  - **Gerar o PDF/A sincronamente dentro de `RegistrarEmpenho`** (renderização é CPU-bound, não é rede) mas publicar o binário no object store ainda dentro da mesma transação — rejeitada: o upload ao object store é efeito externo (rede) mesmo que o cálculo do PDF não seja; manter os dois juntos no worker (b) evita uma exceção a mais ao ADR-0004 e mantém `RegistrarEmpenho` enxuto.
