# ADR-0043 · Frontend: forms em React Hook Form + fronteiras hexagonais (domínio/schema/caso de uso)

- **Status:** Aceita
- **Data:** 2026-08-01
- **Contexto:** RAZ-202 pede a migração de `EmpenhoForm.tsx` (controlado na mão — um `useState<Campos>` + uma função `validar()` reimplementando regra de valor a cada formulário) para React Hook Form, mas o foco pedido pela issue é a **abstração arquitetural**, não só trocar a lib: sem uma fronteira explícita, cada novo formulário (liquidação/pagamento/dotação) reimplementaria a mesma regra de UUID/dinheiro/data já validada em outro lugar, e o form acabaria falando com o client de API direto — o oposto da separação `domain`/`application`/`infra` que [ADR-0041](./0041-frontend-requests-abortaveis-e-camada-de-caso-de-uso.md) já estabeleceu para o caso de uso.
- **Decisão:**
  1. **Domínio framework-free** (`features/execucao/domain/empenho.ts`): value objects de identidade (`DotacaoId`/`CredorId`/`UnidadeGestoraId`/`ContratoId`) via a fábrica genérica `criarTipoIdVO` (`shared/domain/uuidVO.ts` — mirror funcional dos `record XxxId(UUID valor)` de `execucao-domain`) e predicados puros (`isTipoEmpenhoValido`, `isExercicioValido`, `isDataFatoValida`, `isTextoObrigatorioValido`). Zero import de React/RHF/zod — mesma garantia de "regra testável sem framework" que [ADR-0041](./0041-frontend-requests-abortaveis-e-camada-de-caso-de-uso.md) já aplica ao caso de uso. `Money` (dinheiro decimal) já existia framework-free em `shared/lib/dinheiro.ts` e é reusado, não duplicado.
  2. **Schema deriva do domínio, não reimplementa a regra** (`features/execucao/domain/empenhoSchema.ts`): cada campo do `empenhoSchema` (zod) chama o predicado/`.isValid` do VO correspondente — a mensagem de erro mora no schema, a regra de valor mora em `empenho.ts`. Único import externo deste arquivo é `zod`; RHF consome o schema via `zodResolver`, mas a verdade de cada regra é sempre o domínio. Campos permanecem `string` (shape bruto de `<input>`/`<select>`) — a conversão para os tipos finais (`number`, `Money`) só acontece na fronteira com o caso de uso, nunca aqui.
  3. **Hook reutilizável `useFormDeAgregado`** (`shared/forms/useFormDeAgregado.ts`) encapsula RHF + `zodResolver` + a chamada do caso de uso: cada formulário só declara `schema`, `valoresIniciais`, `paraInput` (campos validados → input do caso de uso) e `executar` (o caso de uso em si, nunca o client de API). É o **driving adapter** (borda de UI) — conhece RHF/zod, nenhuma regra de domínio mora aqui. Falha de `executar` vira `form.setError('root.envio', …)`; sucesso reseta o form preservando `isSubmitSuccessful` (`keepIsSubmitSuccessful: true`) para a UI conseguir mostrar "registrado" por um instante.
  4. **`application/registrarEmpenho.ts` ganha `paraEmpenhoRequest`** (mapeamento estrutural campos→`EmpenhoRequest`, sem revalidar — o resolver do RHF já barrou o submit se algum campo violasse o domínio; revalidar seria a "regra de valor em dois lugares" que a issue proíbe). O caso de uso em si (`registrarEmpenho`) não muda: continua exatamente o que [ADR-0041](./0041-frontend-requests-abortaveis-e-camada-de-caso-de-uso.md) definiu, sem import de React/RHF/React Query — o guardrail `fronteira-application-sem-react.test.ts` (que já listava `react-hook-form` como lookalike permitido) continua verde sem alteração.
  5. **Wrappers RHF-compatíveis dos campos do design system, sem tocar `@siafic/design-system`:** `FormSection`/`FormSection.Field`/`.Select`/`.Error` (RAZ-100/[ADR-0032](./0032-frontend-monolito-modular-feature-based.md)/[ADR-0033](./0033-frontend-composicao-proibicao-prop-drilling.md)) já são um compound component controlado por um único Context `{values, errors, onChange}` — `shared/forms/formSectionAdapterRHF.ts` (`useFormSectionRHF`) só traduz um `UseFormReturn` do RHF para esse mesmo contrato (`form.watch()`/`formState.errors`/`form.setValue`), então `<FormSection {...useFormSectionRHF(form)}>` recebe os subcomponentes existentes sem qualquer mudança no pacote do design system. Para o `Select` rico (typeahead/assíncrono, RAZ-122/145) — que `EmpenhoForm` ainda não usa, mas liquidação/pagamento/dotação vão precisar para os pickers de dotação/credor/unidade gestora — `shared/forms/campoSelectRHF.tsx` (`CampoSelectRHF`) faz o mesmo via `Controller`, natural porque `Select` já é controlado por `value`/`onChange` (a mesma forma que o `field` do `Controller` expõe).
  6. **`EmpenhoForm.tsx` migrado como referência**: usa `useFormDeAgregado` + `useFormSectionRHF`; não importa `execucaoClient` nem fala com a API — só chama `useCriarEmpenho` (que por sua vez chama o caso de uso). Os mesmos 11 campos, mesmos rótulos/mensagens de erro (o teste de integração `fluxo-execucao.test.tsx`, que navega por `getByLabelText`, continua verde sem alteração).
  7. **Testes seguem a mesma fronteira que testam:** `empenho.test.ts`/`empenhoSchema.test.ts`/`registrarEmpenho.test.ts` (domínio/schema/`paraEmpenhoRequest`) são framework-free (`vitest` puro, sem `@testing-library/react`); `useFormDeAgregado.test.tsx`/`EmpenhoForm.test.tsx` usam RTL porque testam o driving adapter (hook + componente), não o domínio.
- **Consequências:**
  - **+** Nenhuma regra de valor duplicada: um UUID inválido, uma data de calendário inexistente (`2026-02-30`) ou um enum de tipo errado são rejeitados pelo mesmo predicado em `empenho.ts`, chamado tanto pelo schema quanto (indiretamente) pela mensagem de erro exibida.
  - **+** Próximo formulário (liquidação/pagamento/dotação) reusa `useFormDeAgregado` + os wrappers de campo sem reescrever plumbing de RHF; só declara domínio/schema/caso de uso próprios.
  - **+** `application/`/`domain/` continuam testáveis sem montar árvore React — o caso de uso não mudou de assinatura, só ganhou `paraEmpenhoRequest` ao lado.
  - **−** `useFormSectionRHF` usa `form.watch()` sem argumento, que assina o formulário inteiro — toda tecla re-renderiza a seção inteira, abrindo mão do ganho de performance de inputs não controlados do RHF. Aceito porque `FormSection.Field`/`.Select` (design system) são controlados por Context, não por `register`/`ref` — não há como um `Controller` por campo se conectar a eles sem mudar a API pública do `@siafic/design-system`. Follow-up (dono: Rafael + Paula): se um formulário futuro sentir o custo de re-render, avaliar campos do DS que aceitem `value`/`onChange` diretos (não só via Context de `FormSection`), permitindo `Controller` por campo.
  - **− (armadilha registrada para não repetir):** um `.refine((v) => XxxId.isValid(v), …)` em zod, quando `isValid` é um *type predicate* (`v is UuidVO<Marca>` — como os VOs de `criarTipoIdVO`), faz o zod **inferir narrowing e vazar o branded type para `z.infer`** (`CamposEmpenho['dotacaoId']` virava `UuidVO<'DotacaoId'>`, não `string`) — quebrou `tsc -b` em cascata (valores iniciais, `paraEmpenhoRequest`, testes). Correção: anotar o retorno do callback como `(v): boolean => …` explicitamente, suprimindo a inferência. Guardar isso para qualquer refine futuro que chame um VO/`isValid` tipado como predicate.
  - **− (armadilha de sintaxe registrada):** um comentário `/** … */` que cite um caminho glob como `` `features/*/application/` `` **fecha o comentário cedo** — o `*` seguido de `/` é lido como o fechamento `*/` do bloco, não como texto. É por isso que o código já existente (`fronteira-application-sem-react.test.ts`, ADR-0041) usa `` `features/<feature>/application/` `` com placeholder em vez do glob literal; este ADR bateu o mesmo problema (quebrou `vite`/`oxc` com "Expected a semicolon") antes de adotar a mesma convenção — manter `<feature>` (ou equivalente) em comentários daqui em diante, nunca `*` literal seguido de `/`.
- **Alternativas consideradas:**
  - **Tornar `FormSection`/`Select` do `@siafic/design-system` nativamente cientes de RHF** (aceitar `register`/`Controller` na própria API pública do pacote): rejeitada por ora — acoplaria um pacote pensado para ser agnóstico de forms lib (consumido só por este app hoje, mas desenhado como "pacote independente", [ADR-0036](./0036-design-system-pacote-independente.md)) a uma escolha de app. O wrapper por fora (`shared/forms/`) resolve sem mexer na API pública do DS; revisar só se essa restrição custar caro de verdade (ver consequência do `watch()` acima).
  - **Colocar o schema zod dentro do próprio `empenho.ts` (um arquivo só de domínio):** rejeitada — misturaria a única dependência de terceiro (`zod`) com os VOs puros; separar em `empenhoSchema.ts` deixa explícito que só ele depende de zod e que o domínio continua zero-dependency.
  - **`paraEmpenhoRequest` revalidar via `VO.parse()` em vez de mapear estruturalmente:** rejeitada — o resolver do RHF já barrou o submit se um campo violasse o domínio; revalidar seria uma segunda cópia da mesma regra (proibido pelo princípio 3 da issue), não uma proteção adicional real.
  - **Outra lib de formulário (Formik, etc.):** fora de escopo — a issue já pede RHF especificamente, que tem o melhor suporte a resolver zod (`@hookform/resolvers/zod`) das opções do ecossistema.
