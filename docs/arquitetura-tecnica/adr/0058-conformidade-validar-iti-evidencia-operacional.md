# ADR-0058 · Conformidade VALIDAR/ITI é evidência operacional anexada ao dossiê do documento assinado (não integração no adapter)

- **Status:** Aceita
- **Data:** 2026-08-02
- **Contexto:** RAZ-249 é o resíduo externo (2/2) do delta da assinatura qualificada ICP-Brasil (RAZ-208), extraído de RAZ-246. O caminho qualificado via escopo `icp_brasil` e a multiassinatura incremental **já estão implementados** (RAZ-208); resta a conformidade **VALIDAR/ITI**. O serviço público do ITI (`validar.iti.gov.br`) valida assinaturas por **upload/QR Code e emite um relatório HUMANO** — **não há API servidor-a-servidor estável** para automatizar no adapter (mesma classe de restrição do SICONFI em [ADR-0049](./0049-submissao-siconfi-passo-assistido.md)). O código já reflete essa fronteira: `ServicoAssinaturaGovBrAvancada#verificar` faz a **checagem local** (integridade + cadeia + revogação OCSP/CRL, itens 6 e 10 da [spec transversais/01](../../transversais/01-assinatura-eletronica.md)) e o comentário em `ServicoAssinaturaGovBrAvancada.java:163-167` já marca o relatório VALIDAR como **evidência operacional externa**. A spec transversais/01 §"O que NÃO preciso implementar" fixa: **"Validador nacional → usar o Validador do ITI"**. Falta a **decisão de processo + a primeira evidência** — não engenharia no adapter.
- **Decisão:**
  - **A conformidade VALIDAR/ITI é evidência operacional, não integração de código.** Ratifica-se a fronteira já existente: o teto automatizado (F0/F1) é a checagem local de `verificar(...)` (integridade + cadeia + revogação), registrada na trilha; o **relatório de conformidade do VALIDAR** é produzido **fora de banda** por upload do PDF assinado em `validar.iti.gov.br`. Nenhuma promessa de chamada M2M ao validador.
  - **O relatório é anexado ao dossiê de auditoria do documento assinado**, ancorado às **mesmas chaves** que o evento `assinatura_eletronica` já grava (`idTransacao` + `hashSha256Base64` + URI do documento — `ServicoAssinaturaGovBrAvancada.java:201-215`): o relatório VALIDAR é depositado no **object store/GED** ([ADR-0009](./0009-documentos-object-store.md)/[ADR-0018](./0018-object-store-s3-compativel.md), cifrado em repouso e coberto pelo backup) e listado no **dossiê de aceite** do ente. Padrão idêntico ao da evidência operacional de RAZ-38 e ao provisionamento de RAZ-24 — **sem engenharia no adapter**.
  - **Owner da primeira evidência: ENTE-PILOTO/OWNER.** A evidência exige uma assinatura **qualificada ICP-Brasil real**, que só existe no ambiente do ente (mesma classe do smoke test e2e e de RAZ-38, [docs/14](../../14-status-feito-pendente.md)). O procedimento operacional está documentado em [`docs/operacao/RAZ-249-runbook-evidencia-validar-iti.md`](../../operacao/RAZ-249-runbook-evidencia-validar-iti.md).
  - **Gancho de automação futura (fora do escopo F1):** se/quando houver demanda, o relatório pode ser capturado como um `EventoAuditoria` de tipo `conformidade_validar_iti` **anexado à hash-chain** (reusando `AuditoriaEscrita#append`, referenciando a mesma URI/`idTransacao`) — preserva o invariante append-only ([ADR-0005](./0005-trilha-append-only-hash-chain.md)) sem tabela mutável nova. Registrado como hook, **não exigido agora** (a captura em F1 é o depósito no object store + dossiê).
- **Consequências:** fecha a metade "definir + documentar" de RAZ-249 sem acoplar o produto a uma API que não existe; a evidência é auditável (TCE/ANPD) e amarrada às mesmas chaves do documento. RAZ-249 permanece **bloqueada apenas na primeira evidência**, cujo owner nomeado é ENTE-PILOTO/OWNER — destrava RAZ-246 (→ resíduo de RAZ-208) quando a evidência for coletada. A verificação automatizada plena de DOC-ICP-15 continua **F2** (faseamento da spec transversais/01).
- **Alternativas consideradas:**
  - **Integração M2M com o `validar.iti.gov.br`** — impossível: não há API servidor-a-servidor estável; só upload/QR Code + relatório humano. Mesma razão de [ADR-0049](./0049-submissao-siconfi-passo-assistido.md).
  - **Scraping/robô do portal VALIDAR** — rejeitada: frágil, sem contrato estável, risco de violar termos de uso; o ganho não compensa (a assinatura qualificada já exige o certificado/token do responsável no ambiente do ente).
  - **Reimplementar a verificação DOC-ICP-15 in-house como "validador nacional"** — rejeitada para F1: reproduz o validador oficial que a spec manda **consumir** (transversais/01 §"O que NÃO preciso"); o ITI é a referência oficial. Verificação DOC-ICP-15 automatizada é escopo **F2**.
