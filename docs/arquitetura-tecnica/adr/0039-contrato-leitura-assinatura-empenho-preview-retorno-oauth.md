# ADR-0039 · Contrato de leitura para assinatura do empenho — preview de documento, enriquecimento do read model e retorno do OAuth gov.br

- **Status:** Proposta
- **Data:** 2026-07-26
- **Contexto:** [RAZ-141](../fluxo-execucao-operador-contrato-api.md#55-tela-nota-de-empenho--assinatura-raz-141-papel-ordenador) (Figma: preview + assinar gov.br) desenhou a tela "Nota de empenho — Assinatura" sobre o código real de `AssinarEmpenho`/`AssinaturaEmpenhoController`/`AssinaturaGovBrOAuthController` (RAZ-103, [ADR-0017](./0017-bff-oauth-assinatura-govbr.md), [ADR-0027](./0027-wiring-empenho-assinatura-gate-interativo.md)), que já estão em `master` e funcionam — o gap não é a escrita. Três lacunas de **leitura/borda HTTP** bloqueiam a tela de virar produto real:
  1. `Empenho.documentoPendenteUri()`/`DocumentoAssinadoEmpenho.pdfAssinado()` são estado interno do domínio; `ArmazenamentoDocumentos.ler(URI)` ([ADR-0009](./0009-documentos-object-store.md)) é porta de plataforma, nunca amarrada a um `@RestController` — não existe forma de o navegador buscar/renderizar o PDF (pendente ou assinado).
  2. Nenhum endpoint devolve o `Empenho` com `status`/metadados de assinatura por `id`. A única leitura existente, `GET /entes/{enteId}/execucao/empenhos` (RAZ-121, `ExecucaoConsultaController`), devolve `status` mas não `documentoPendenteUri`, `hashSha256`, `idTransacao` nem `nivel` — a tela não tem de onde ler o que precisa mostrar.
  3. `GET /assinatura/oauth/callback` ([`AssinaturaGovBrOAuthController`](../../bootstrap/src/main/java/br/contabil/assinatura/AssinaturaGovBrOAuthController.java)) devolve `204 No Content` (sucesso) ou `400`/`502` JSON **direto ao navegador do gov.br**, que é quem redireciona o operador de volta para lá após o login. `AssinaturaGovBrOAuthProperties.redirectUri` não tem valor-padrão — nada no código aponta esse retorno para uma rota do SPA. Sem isso, não existe onde renderizar o estado "Retornando do gov.br" (§5.5) nem como voltar à Tela 1b — o operador para numa aba com JSON cru ou em branco.
- **Decisão:**
  1. **`GET /entes/{enteId}/execucao/empenhos/{id}`** — devolve o `Empenho` completo por id, incluindo `status` e um bloco `documento` (`pendenteUri` opaco enquanto `PENDENTE_ASSINATURA`/`ASSINATURA_REJEITADA`; `assinado: { hashSha256, idTransacao, nivel, signatario (CPF mascarado), assinadoEm }` quando `ASSINADO`, `null` antes disso). `Acao.LER`, mesma forma de `GET /empenhos` (RAZ-121) mas para 1 item — hoje só existe a listagem, nenhum `GET` por id. `pendenteUri`/URIs do object store **nunca** vazam cru no JSON (viola o isolamento multi-tenant estrutural do ADR-0009 §RAZ-45 se o cliente resolver a `s3://` direto) — o campo é só um indicador de presença; o binário sai pelo endpoint (2).
  2. **`GET /entes/{enteId}/execucao/empenhos/{id}/documento`** — stream `application/pdf` do documento atual do empenho (assinado se existir, senão o pendente), lendo via `ArmazenamentoDocumentos.ler(URI)` internamente; o controller resolve a `URI` a partir do agregado (nunca aceita URI do cliente — mesma disciplina de borda fina que os demais controllers de consulta, `guardiao-arquitetura`). `Acao.LER` sobre `execucao:empenho`, sem MFA (mesma classe de leitura que `GET .../empenhos`). Alternativa de implementação (URL assinada do object store com TTL curto vs. proxy/stream pelo backend) é decisão de infra, não deste ADR — qualquer uma resolve o contrato de UI (`<a href>`/`<iframe>` para o mesmo path).
  3. **`redirect_uri` do OAuth de assinatura passa a apontar para uma rota do SPA**, não para `/assinatura/oauth/callback` diretamente. `AssinaturaGovBrOAuthController.callback` deixa de devolver `204`/JSON de sucesso e passa a devolver **`302` para `siafic.assinatura.govbr.oauth.frontend-retorno-uri`** (nova propriedade, ex. `https://app.../execucao/empenhos/{id}/assinatura/retorno?resultado=ok|erro`) — o SPA já é quem, nessa rota, decide se chama `POST .../assinatura` (se ainda não foi chamado) e renderiza o estado "Retornando do gov.br" → sucesso/erro. Erro do próprio OAuth (`oauth_recusado`, `state_invalido`, `code_ausente`, `AssinaturaGovBrOAuthProvedorIndisponivelException`) também vira `302` com `?resultado=erro&codigo=...` em vez de um corpo JSON que o navegador do gov.br não tem como exibir de forma útil — o SPA decodifica e mostra a mensagem certa (mesma taxonomia `ErroContrato.codigo()` do resto do contrato, §6.1, só que entregue por query param porque é um redirect de navegador, não uma resposta de `fetch`).
  4. **Sem mudança nos três endpoints já existentes** (`POST .../assinatura`, `GET .../oauth/iniciar`, o próprio `.../oauth/callback` continua existindo, só muda o que devolve no sucesso) — este ADR só adiciona leitura, não revisita ADR-0017/0027.
  5. **`contrato-provisorio.yaml` ganha os 5 endpoints do fluxo de assinatura** (os 2 novos de leitura acima + os 3 já implementados: `POST .../assinatura`, `GET .../oauth/iniciar`, `GET .../oauth/callback`), com uma nota explícita de que os 3 últimos usam `HttpSession`/cookie e não `Authorization: Bearer` — a única exceção documentada às convenções do §6.1 do contrato de execução.
- **Consequências:** duas issues novas de backend (`[BE] GET /empenhos/{id}` — leitura por id com bloco `documento`; `[BE] GET /empenhos/{id}/documento` — bridge de download/preview) mais uma issue pequena e cirúrgica em cima de código já existente (`[BE] redirect_uri do callback OAuth de assinatura aponta para o SPA, não devolve 204/JSON cru` — muda `AssinaturaGovBrOAuthController.callback` + `AssinaturaGovBrOAuthProperties` + config). Nenhuma toca `AssinarEmpenho`/`ServicoAssinatura`/o domínio de assinatura em si. A tela Figma (RAZ-141, páginas `17`/`18`) já está desenhada contra este contrato proposto, com "Aviso de Gap" inline nos dois pontos que dependem de (1)/(2) — os 5 estados (pendente/confirmação/retorno/assinado/rejeitada) não mudam de forma quando o backend fechar, só passam a ler dado real em vez de maquete.
- **Alternativas consideradas:**
  - **Expor a `s3://` URI crua no `GET /empenhos/{id}` e deixar o cliente buscar direto no object store** — rejeitada: quebra o isolamento multi-tenant estrutural do ADR-0009 (a checagem de prefixo por `ente` vive na ponte de assinatura, não em política de bucket acessível por navegador) e vaza detalhe de infraestrutura (nome do bucket, layout de chave) num contrato de API público.
  - **Backend devolver o PDF embutido em base64 dentro do JSON de `GET /empenhos/{id}`** — rejeitada: infla o payload da leitura "resumo" com um binário que só é necessário quando o operador efetivamente abre o preview; mantém os dois casos de uso (ver metadados vs. ver o PDF) como dois `GET`s distintos, cacheáveis/streamable independentemente.
  - **Manter `/assinatura/oauth/callback` devolvendo JSON e resolver o "retorno" só no front, fazendo polling de `GET /empenhos/{id}` até `status` mudar** — rejeitada: não resolve o problema real (o navegador ainda pousa numa aba de JSON cru controlada pelo backend depois do gov.br, sem nenhuma UI); o polling ainda seria necessário *depois* do redirect para o SPA, não substitui o redirect.
  - **Front-end registrar o próprio domínio como `redirect_uri` direto no gov.br (pulando o backend no retorno)** — rejeitada: o `code`→`token` exchange (PKCE) precisa do `client_secret` server-side (ADR-0017); o navegador não pode trocar o `code` sozinho, então o callback **tem** que passar pelo backend primeiro — o que muda é só o que o backend faz *depois* de gravar o token (redirecionar para o SPA em vez de responder direto).
